## 地图系统架构调研 + 格子化方案设计（咨询，未落地代码）

### 现状事实（已核实）
- `server/config/map_data.json`：8 个地图节点，`x/y` 坐标跨度 0→2000，`connections` 是**单链**（1→2→…→8），无格子。
- `WorldMovementService.nearestMap()` 用最近节点（Voronoi）判定归属 → 境界门槛实际靠玩家"敢不敢点过去"，
  且 `MAX_STEP=80` 一次点击可跨越极远距离。
- `playerMapPosition` 的 `visited_nodes` / `exploration_progress` / `resource_gather_count`
  **是死字段**：仅在 `routes/map.js:102-105` 读出回显，全项目无写入方。
- 内容是"地图级"列表（每个区域 3~4 种资源/怪），探索走 `map/explore/*` 次数制历练，与位置无关。
- 并存两套移动：`routes/map.js` 的 `start-move`（延时、耗灵力）+ `WorldMovementService`（即时连续坐标）。
- 前端 `WorldMapPanel.vue` 已有 `view.scale` 的 LOD 分档（0.35 / 0.8），可直接扩成三档。

### 给出的方案结论（待用户决策，尚未实现）
- **不做"全世界一张大 grid"，做"分层中等 grid"**：每层 12×12（新手）/ 16×16（主舞台）/ 16×16+80%迷雾（高层位面），
  层间仍用节点图/传送阵。理由是现有 `type` 字段（country/sect/mountain vs world）天然分层。
- 格子尺寸：`cell_size=10` 世界单位，`cell_px=40`，一屏可见约 22×15 格。
- 单格耗时按地形配置：平原 30s / 山地 60s / 水域 90s → 穿越一层 8~12 分钟。
- 渲染四通道：底色=地形、图标=最强内容（一格一个）、角标=状态、细线=区域边界；**迷雾是核心**（兼掩盖内容不足）。
- 配置三段式：`terrain_zones` 分区 + `seed` 确定性 PRNG 生成 + `overrides` 手工覆盖，禁止手写全格。
- 保留 `pos_x/pos_y` 连续坐标，用 `floor(x/cell_size)` 推导格子 → 插值/广播/防作弊不用重写。
- `start-move` 收窄为跨层传送，格内走即时移动，避免绕过格子门槛。

### 最大前置依赖
内容池不足：256 格需 200+ 内容点，当前全地图资源+怪物不足 40 条。
**先扩 `resource_data.json` / 怪物池，再上格子**，否则格子越多越空洞。

## AI 配置模块简化：移除官方厂商预置，仅保留 OpenAI 兼容接口（已落地）

### 诊断
- `server/config/ai_config.json` 预置了 13 个 provider（openai/anthropic/qwen/zhipu/azure/xiaomi/deepseek/moonshot/yi/baichuan/minimax/siliconflow/custom），需逐个维护，已过时。
- `AIService` 同时维护 openai / anthropic 两套协议分支（`getHeaders` / `getEndpoint` / `buildRequestBody` / `parseResponse`）。
- GM 后台"测试连接"失败误报根因：旧判据要求 `choices[0].message.content` 非空，而推理型模型在 `max_tokens:10` 时正文为空 → 被误判为「响应结构不符合预期」（即截图里的失败）。

### 改动
- `server/config/ai_config.json`：providers 只留 1 个 `openai`（name「OpenAI 兼容接口」，endpoint/baseUrl/model 留空由后台填）。
- `AIService.js`：删除 `inferProtocol()`，`protocol` 恒为 `'openai'`；四个协议分支收敛为 OpenAI 兼容单一路径；`parseResponse` 遇空正文返回明确 error 交给模板降级。
- `routes/admin_ai.js`：test 接口去掉 anthropic 分支；判定放宽为「HTTP 200 且 `choices` 为非空数组即成功」；测试 `max_tokens` 10 → 32。
- 前端 `AIConfig.vue`：去掉"提供商"下拉与"通信协议"下拉，接口类型改只读展示；`admin_ai.ts` 的 `protocol` 类型收敛为 `'openai'`。
- 同步 `docs/openapi.json`、`.env.example`（`AI_PROVIDER` 不再需要）、`models/ai_config.js` 与 `ConfigSurface.test.js` 注释（13 provider → 单一）。

### 验证
- `cd server && npx jest --silent` → 56 suites / 808 tests 全通过。
- `client` 侧 `vite build` 无报错。
- 注意：DB 表 `ai_configs.protocol` 列保留（恒 openai，未做 migration）；`provider` 唯一索引仍在，意味着同一时间只允许一条启用配置。

## 全项目时间统一为北京时间 + 网络错误提示细化（已落地）

### 问题
1. GM 后台点"测试"报"网络错误，请检查网络连接"，无从定位是接口问题还是代码问题。
2. 各处时间显示不是北京时间（截图里 `last_tested_at` 直接渲染原始 ISO，显示 `...T15:42:11.000Z`，UTC）。

### 时间统一方案（关键约定）
- 新增 `client/src/utils/time.js`：**固定 UTC+8**，不依赖 `Intl` 时区库、不受系统时区影响。
  做法是把时间戳整体 +8h 后用 `getUTC*` 读"墙上时间"。
  - `formatBeijing(v, { seconds, showDate, showTime, dateStyle:'full'|'short', fallback })`
  - `formatBeijingDate` / `formatBeijingClock` / `nowBeijing` / `parseTime` / `toBeijingDate`
  - `parseTime` 对**无时区**字符串（`2026-09-21 15:42:11`、`2026-09-21`）按北京时间解读，
    避免被浏览器本地时区二次偏移。
- 替换范围：前端 **30 个文件**（GM 后台 15 个 + 玩家端 panels 23 个 + GlobalChat / DeathOverlay / ChangelogModal / data/changelog.js / utils/format.js）。
  原实现多为 `new Date(x).getHours()/getMonth()` 手拼或 `toLocaleString('zh-CN')`，全部收敛为 `formatBeijing`。
- 后端 `server/index.js`：在 `dotenv.config()` 之后、业务模块 require 之前设置 `process.env.TZ='Asia/Shanghai'`（`.env` 显式配置优先）。
  DB 层 `config/database.js` 原本已是 `timezone: '+08:00'`。

### 错误提示细化（`client/src/api/index.ts`）
- 401/403/404/500 现在都带上 `error.config.url` 便于定位；500 优先显示后端 `data.message`。
- `error.request`（无响应）分支按 `error.code` 细分：
  `ECONNABORTED`/timeout → "请求超时（N 秒）：URL"；`ERR_CANCELED`；`ERR_NETWORK`；其它带 `error.message`。
  不再一律提示"网络错误，请检查网络连接"。

### AI 测试超时链路（修复"干等一条网络错误"）
- 前端 `testAiConfig` 单独设 `timeout: 120000`（原本吃默认 30s，会先于后端超时）。
- 后端 `routes/admin_ai.js` 测试请求超时改为 `Math.min(Math.max(config.timeout, 10000), 90000)`，
  保证后端一定先返回并给出具体失败原因。

### 验证
- `client` 侧 `vite build` 成功（检查 dist 产物时间戳确认）。
- `cd server && npx jest --silent` → 56 suites / 808 tests 全通过。

## 地图格子化方案 · 第二轮修订（用户反馈后，仍未落地代码）

### 用户的关键修正（已采纳）
1. **不需要每格都有内容**，空格子是正常且必要的；空格还应承载玩家自建内容（洞府、遗迹）。
   → 我上一版把"空格"当缺陷是错的。空格的三重价值：节奏留白 / 玩家占用 / 资料片扩展位。
2. **尺寸取 10×10 或 12×12**，不要 16×16。
   → 直接把"内容池不足"这个我认定的最大前置依赖**降级为非阻塞项**：
     10×10=100 格只需 25~30 个内容点，12×12=144 格只需 36~45 个；现有全地图资源+怪物约 40 条基本够用，
     仅需按地形归类，无需先大规模扩池。

### 新核实的两个关键事实
- `server/models/playerCave.js`：**洞府完全没有位置字段**（无 map_id/pos_x/cell），`player_id` unique，
  纯虚拟个人空间。→ "格子上建洞府"是**纯新增，无数据迁移成本**。
- `server/models/caveLegacy.js`：**已有"坐化遗府"系统**（配套 caveLegacyItem / Participant / DistributionLog 四张表），
  但目前由 `opened_by_admin` 管理员手动开启、与地图无关。→ 格子化可给它补上位置维度：
  **遗府生成在玩家洞府所在格，他人需走到该格才能分宝**，现有纯 UI 活动升级为空间玩法。

### 修订后的尺寸结论
- **统一 12×12，新手层用迷雾只开中间 10×10**（per-layer `size` 配置即可，不统一也无代码成本）。
- 修正上一版：因 `terrain_zones` 用 `rect` 自由矩形，区域划分本就不要求整除，"12 比 10 好整除"理由不成立。
- 空格仍建议给零成本反馈：低概率触发 `adventure_event_data.json` 的 `peaceful` 类事件 + 已探索 ✓。

### 新增的前置决策（引入"玩家占格"后产生，上一版完全没覆盖）
1. 洞府应为**逻辑门牌**（格子只是入口标记，进去仍是 `player_caves` 虚拟空间，不阻挡通行），
   不能做物理独占——144 格里 30% 可建造仅 43 格，几百玩家必然抢爆。
2. 同格多洞府：先到先得 + 角标显示数量（⛰×3）。
3. 可建造地形（限山地/洞窟/林地）需在 `cave_data.json` 做成配置项。
4. 弃坑洞府超 N 天未登录 → 转为 `caveLegacy` 遗府，**把洞府与遗府两个系统串成闭环**（最看好这条）。
